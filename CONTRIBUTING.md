# Как вносить правки

Документ описывает порядок внесения изменений в репозиторий: именование
веток, пул-реквесты, проверки CI и требования к коммитам. Сборка,
необходимые инструменты и устройство дерева описаны в [README](README.md).

## Ветки и пул-реквесты

- Изменения попадают в `main` только через пул-реквест, у которого успешно
  пройдены все обязательные проверки CI. Набор правил (ruleset) ветки
  `main` на GitHub запрещает прямой push и force-push, требует линейной
  истории и допускает вливание только способом squash: пул-реквест
  объединяется в один коммит, так что каждому пул-реквесту соответствует
  один коммит в `main`. После вливания GitHub удаляет ветку пул-реквеста
  автоматически.
- Изменение разрабатывается в отдельной ветке с именем `bukvitsa-<тема>` из
  строчных латинских букв и дефисов. Пул-реквест открывается из этой ветки
  в `main` и содержит изменения одной темы.
- Заголовок пул-реквеста становится заголовком его коммита в `main`, а
  описание — телом этого коммита. Поэтому заголовок и описание пишутся
  по-русски и по тем же правилам, что и сообщение коммита (см. раздел
  «Коммиты»), и правило 2 распространяется на них.
- Уже отправленную ветку не переписывают: force-push и rebase отправленных
  коммитов не допускаются. Это требование автоматически не проверяется,
  его соблюдают сами участники. Перед вливанием ветка должна содержать
  текущую `main`. Если ветка отстала от `main` или конфликтует с ней, `main`
  вливается в ветку командой «Update with merge commit» кнопки
  «Update branch» (не «Update with rebase»). Конфликт разрешается в
  редакторе GitHub «Resolve conflicts» или локально: текущая `main` этого
  репозитория сливается в ветку, конфликт разрешается в коммите слияния, и
  результат отправляется обычным push.

## Проверка (CI)

Workflow [`.github/workflows/ci.yml`](.github/workflows/ci.yml) выполняется
на раннере Windows. Он собирает дерево в конфигурациях Debug и Release,
запускает тесты и открывает окно читалки. Workflow
[`.github/workflows/commits.yml`](.github/workflows/commits.yml) проверяет
коммиты пул-реквеста, его заголовок и описание (см. раздел «Коммиты»); он
запускается и при изменении заголовка или описания, сборка при этом не
повторяется.

- Библиотека wxl используется на коммите, указанном в
  [`tools/wxl.json`](tools/wxl.json). Задание `wxl-revision` проверяет, что
  этот коммит входит в `main` репозитория wxl. Если изменению нужна более
  новая версия wxl, коммит в `tools/wxl.json` меняется после того, как
  нужное изменение wxl влито в её `main`; до этого проверка `wxl-revision`
  завершается ошибкой.
- Обязательные проверки: `build (Debug)`, `build (Release)`, `wxl-revision` и
  `commits`.

## Коммиты

Сообщение коммита пишется по-русски связным текстом: что изменено и почему.
Задание `commits` проверяет каждый коммит пул-реквеста, а также его заголовок
и описание на соответствие правилам ниже; в сообщении об ошибке указан номер
нарушенного правила.

1. Адреса электронной почты автора и коммиттера имеют вид
   `…@users.noreply.github.com` (настройка «Keep my email address private»);
   совпадать они не обязаны. Коммиттер `GitHub <noreply@github.com>`
   указывается у коммитов, которые создаёт сам GitHub (слияния через
   «Update with merge commit» и «Resolve conflicts», объединение
   пул-реквеста при вливании); такой коммит допускается только с подписью,
   которую подтверждает GitHub.
2. Сообщение коммита не содержит строк `Co-Authored-By` (у коммита один
   автор), строк-баннеров и строк-трейлеров со ссылками. То же относится к
   заголовку и описанию пул-реквеста: из них составляется сообщение коммита,
   в который пул-реквест объединяется при вливании.
3. Скрытые каталоги и файлы (с именем, начинающимся с точки) в репозиторий
   не добавляются, за исключением перечисленных в проверке.
4. Подписывать коммит не обязательно; если подпись есть, GitHub должен её
   подтверждать (Verified).
5. Коммит слияния допускается, только если он вливает `main` в ветку: у
   него два родителя, и второй из них — коммит `main`. Любой другой коммит
   слияния проверку не проходит. История самой `main` остаётся линейной,
   потому что каждый пул-реквест вливается в неё одним коммитом.

## Перед пул-реквестом

Перед открытием пул-реквеста достаточно собрать и проверить в конфигурации
Debug только то, что затронуто изменением; полную матрицу конфигураций
проверяет CI. Команды выполняются из корня дерева:

```
tools\build.ps1 -Target <цель>
ctest --preset x64-debug -R <тест>
```

Тесты: `fb3_tests`, `mathml_tests`, `typography_tests`, `system_failure.*`,
`bukvitsa_lib_tests`, `bukvitsa_imaging_pool_tests`; читалка — цель `Reader`.
